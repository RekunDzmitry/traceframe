traceframe — data model

Draft · extracted from the HTML prototype (observability.html / data.js / wiki.jsx)

Purpose. Formalize the entities the prototype already renders so a real backend / schema / API can be built against them without re-deriving shape from mock JS.

Conventions #

  • Type definitions are TypeScript-flavored. Treat them as the canonical contract; a concrete implementation may translate to SQL, Protobuf, Pydantic, Zod, etc.
  • ISOTimestamp = RFC 3339 string, always UTC. The prototype stores "14:22:08" as a display string — the real model stores full UTC and lets the UI format.
  • Millis = integer milliseconds. USD = number.
  • Fields tagged ui are presentation-only; a real producer may omit them.
  • Fields tagged derived are computed at read time (backlinks, siblings, ancestor chain). Do not store.

§1 Trace graph #

The core entity: a Trace is a rooted DAG of Nodes representing an agent run, plus alternate branches explored either by the agent (different model) or by a human (experiment from the inline branch panel).

1.1 Trace #

interface Trace {
  id:          TraceId;        // "trc_9f2a" — opaque, stable
  title:       string;         // "Fix: login redirect loop on SSO"
  repo:        string;         // "acme/web"
  branch:      string;         // git branch this run targeted
  startedAt:   ISOTimestamp;
  duration:    Millis;         // wall-clock; freeze at last event for `running` traces
  totalTokens: number;         // sum over all nodes, branches included
  totalCost:   USD;
  status:      TraceStatus;
}

type TraceId     = string;     // "trc_" + 4+ hex chars
type TraceStatus = "running" | "done" | "failed";
Invariants
  • totalTokens / totalCost MUST equal the sum over owned nodes. Denormalized for cheap list rendering; recompute on write.
  • For status: "running", duration is monotone — UI may display a live ticker.

1.2 Node #

Every LLM step, tool call, plan step, or branch experiment is a Node. Nodes form a tree via parent. Multiple nodes may share a parent — those are sibling branches (visible in the tree side-by-side).

interface Node {
  id:       NodeId;         // trace-local, e.g. "n1", "n4a"
  traceId:  TraceId;        // not in prototype's mock; add for storage
  parent:   NodeId | null;  // null only for the root of the main line
  kind:     NodeKind;
  label:    string;         // short tag shown on the node chip
  summary:  string;         // one-line description for the detail header

  // Execution
  model:    ModelId;
  provider: Provider;       // cached from model for filters
  tools:    ToolName[];     // tools invoked from this node
  files:    FilePath[];     // files touched by this node

  // Telemetry
  inputTokens:  number;
  outputTokens: number;
  cost:         USD;       // billed cost for this node only
  latency:      Millis;    // end-to-end
  ttft:         Millis;    // time-to-first-token
  status:       NodeStatus;
  timestamp:    ISOTimestamp;

  // LLM payload
  input:      string;         // full rendered input (system + user + tool_results)
  output:     string;         // assistant response text
  toolCalls:  ToolCall[];
  decision:   Decision;       // the flagship reasoning surface

  // Branch metadata (present only for alt branches)
  isBranch?:    boolean;
  branchLabel?: string;       // "another model", "new approach"
  branchKind?:  BranchKind;

  // UI hints
  highlighted?: boolean;      // ui — pulse the node in the tree
}

type NodeKind    = "plan" | "tool" | "llm" | "experiment";
type NodeStatus  = "ok" | "error" | "running" | "skipped";
type Provider    = "anthropic" | "openai" | "google" | "meta" | string;
type ModelId     = string;
type ToolName    = string;    // search_fs, read_file, edit_file, run_tests, …
type FilePath    = string;    // repo-relative POSIX path

NodeKind interpretation

kindmeaningexample
planLLM step producing a plan; no tool calls.n1
toolNode whose primary action was a tool call. toolCalls.length ≥ 1.n2, n3, n5, n6
llmReasoning step; may also call tools. Distinction from tool is authorial.n4, n4a
experimentHuman-initiated branch from the inline panel. Always isBranch: true.n4b
Invariants
  • parent must reference an existing Node.id in the same trace, or be null.
  • Exactly one node per trace has parent: null.
  • If kind === "tool", then toolCalls.length ≥ 1.
  • isBranch === true ⇒ parent !== null.

Derived at read time derived

interface NodeDerived {
  children:      NodeId[];   // nodes whose parent === this.id
  siblings:      NodeId[];   // share this.parent, excluding this
  ancestorChain: NodeId[];   // root → this (used by the branch panel to build context)
  depth:         number;
}

1.3 Decision #

The centerpiece of the prototype. Every node has one. Answers what did the LLM choose and why in a structured way so a human can audit reasoning without reading the full transcript.

interface Decision {
  goal:    string;             // what this node was trying to accomplish
  options: DecisionOption[];   // considered alternatives
  why:     string;             // tie-break rationale
}

interface DecisionOption {
  label:  string;
  chosen: boolean;            // exactly one option is chosen
  reason: string;
}
Invariants
  • options.length ≥ 1
  • Exactly one option.chosen === true

UI note The detail panel renders three tabs — Structured (goal → options → chosen → why), Annotated (input/output with red/green highlights on bug signal vs. decision), Diff (diff of input vs parent's output). All three read the same Decision + input/output; no extra storage.

1.4 ToolCall #

interface ToolCall {
  name:       ToolName;
  args:       Record<string, unknown>;
  result:     string;         // return summary (truncated)
  resultRef?: BlobRef;        // pointer to full result in blob storage
  latency?:   Millis;
  status?:    NodeStatus;
}

interface BlobRef {
  uri:         string;    // "s3://traceframe/trc_9f2a/n3/read_file.txt"
  bytes:       number;
  contentType: string;
}

1.5 Branching model #

Two kinds of alt branches, both represented as extra Nodes with a shared parent:

type BranchKind =
  | "alt-model"     // agent-internal: same prompt, different model (n4a)
  | "experiment";   // human-initiated from the branch panel (n4b)
  • alt-model branches are created by the agent's runtime and have kind: "llm" | "tool" | "plan".
  • experiment branches are user-initiated and always have kind: "experiment".
  • Both set isBranch: true and populate branchLabel.
  • A branch's children can grow into a full subtree — no structural difference from the main line.
Sibling semantics (resolved)
When a user branches from node N, the new node is created as a sibling of N, not a child: newNode.parent = N.parent. "Branching from n4" means "try a different n4", not "try something after n4". Matches the prototype (n4b.parent === n3).

§2 Branch experiment #

The inline panel on a selected node lets the user re-run the step with a different model / prompt / context. When submitted, it produces a new Node (usually with branchKind: "experiment") rooted at the source node's parent.

2.1 BranchExperimentSpec — runtime payload #

interface BranchExperimentSpec {
  sourceNodeId: NodeId;      // new node's parent = sourceNode.parent (sibling)
  traceId:      TraceId;

  // Model config
  model:           ModelId;
  provider:        Provider;
  temperature:     number;      // [0, 2] typical
  topP:            number;      // (0, 1]
  maxOutputTokens?: number;

  // Prompt
  userMessage: string;          // the task to re-try

  // Context — built from sourceNode's ancestor chain, then user-edited
  context: ContextMessage[];

  // Informational live estimates; recompute server-side
  estInputTokens?:  number;
  estOutputTokens?: number;
  estCost?:         USD;
}

2.2 ContextMessage #

Each message the LLM will see. buildContextChain(node) constructs it from the ancestor chain:

  1. One system message (root system prompt).
  2. For each ancestor node in root→current order:
    • Any <user>…</user> blocks in node.input become user messages.
    • Each node.toolCalls[i] becomes a tool_result message: "${name}(${args}) → ${result}".
    • node.output becomes an assistant message (skip for the branched-from node — that output is what we're re-generating).
// Persisted shape — lives in BranchExperimentSpec.context and goes to the provider
interface ContextMessage {
  role:    Role;
  content: string;
  source:  NodeId | "system";   // attribution in the UI
}

// UI superset — never serialized. The panel strips these before submit.
interface ContextMessageUI extends ContextMessage {
  enabled:   boolean;             // ui — toggle without deleting
  collapsed: boolean;             // ui — fold/unfold in the panel
}

type Role = "system" | "user" | "tool_result" | "assistant";
Invariants
  • role === "system" typically appears once at the start; the model doesn't forbid multiple.
  • source === "system" only for the root system prompt; every other message's source is a real NodeId.
  • enabled and collapsed MUST NOT be persisted. Disabled messages are filtered out before the spec is written or sent; collapsed state is session-local.

2.3 ModelCatalog #

Needed to compute cost estimates live. The prototype inlines this in branch.jsx; production stores server-side.

interface ModelEntry {
  id:                ModelId;
  provider:          Provider;
  inputCostPerMTok:  USD;       // e.g. 3 = $3 per million input tokens
  outputCostPerMTok: USD;
  contextWindow?:    number;    // tokens
  capabilities?:     string[];  // "tool-use", "vision", …
}

2.4 Provider adapters #

The canonical data model (ContextMessage + BranchExperimentSpec) is provider-agnostic. Translation to a provider's native request shape happens in a thin adapter at the HTTP boundary — not in storage, not in the UI.

interface ProviderAdapter {
  provider: Provider;
  toRequest(spec: BranchExperimentSpec, catalog: ModelEntry): ProviderRequest;
  fromResponse(raw: unknown): NodePartial;     // what to persist on the resulting Node
}

Adapter responsibilities:

  • Map our unified Role to native roles. E.g., tool_result → OpenAI {role: "tool"} vs. Anthropic {role: "user", content: [{type: "tool_result", …}]}.
  • Fold temperature, topP, maxOutputTokens into the native params object.
  • Handle streaming → non-streaming reassembly (for persistent Node.output).
  • Normalize token-usage and cost fields back to our units.

Why this boundary. Stored ContextMessage stays portable (re-run the same spec against a new provider without rewriting it), the UI renders one shape, and adding a provider is a new adapter — no migration.

2.5 SavedExperiment #

Sidebar shows "Saved experiments" — named bundles of specs for reuse.

interface SavedExperiment {
  id:        string;                    // "exp_cheap_sweep"
  name:      string;                    // "Cheap model sweep"
  createdAt: ISOTimestamp;
  specs:     BranchExperimentSpec[];     // typically one template × N models
  notes?:    string;
}

§3 Wiki #

Obsidian-style linked notes. Pages keyed by slug; wikilinks [[Page Title]] resolved against the same map at render time.

3.1 WikiPage #

interface WikiPage {
  slug:    WikiSlug;    // map key; used by [[wikilinks]]
  title:   string;      // display title (may differ from slug)
  tags:    string[];    // "runbook", "p1", "resolved", …
  updated: ISODate;     // YYYY-MM-DD
  body:    string;      // markdown with [[wikilinks]]
  links:   WikiSlug[];  // outgoing — denormalized for fast graph queries
}

type WikiSlug = string;  // human-readable: "SSO Proxy"
type ISODate  = string;  // "2026-04-20"
Invariants
  • slug is unique across all pages.
  • Every slug in links must reference an existing page, or render as a dangling wikilink.
  • links regenerable from body via /\[\[([^\]]+)\]\]/g; keep as a denormalized index for cheap backlinks.

3.2 Markdown dialect #

The prototype's renderBody supports a deliberately small subset:

  • # / ## headings
  • > blockquotes
  • 1. ordered list items / - unordered list items
  • Blank lines → paragraph breaks
  • Inline: [[wikilink]] only — no bold/italic/code spans in v1

Any extension should be documented here before expanding the renderer.

3.3 Derived — backlinks & local graph derived #

interface WikiDerived {
  backlinks:  WikiSlug[];            // p where p.links.includes(this.slug)
  localGraph: {
    nodes: WikiSlug[];                 // this + 1-hop neighbors
    edges: [WikiSlug, WikiSlug][];    // directed, following `links`
  };
}

§4 Code graph — AST / semantic model #

Visualization of the codebase as a graph of symbols (modules, functions, constants) connected by typed edges. Traces reference symbols; the code graph and trace graph join on FilePath + symbol id.

4.1 CodeSymbol #

interface CodeSymbol {
  id:        SymbolId;            // unique within a repo; could be a qualified name
  kind:      SymbolKind;
  label:     string;
  parent?:   SymbolId;            // enclosing module (unset for top-level modules)

  // Production additions
  file?:      FilePath;
  signature?: string;            // for fns/consts; UI shows as code block
  line?:      number;

  // Telemetry
  hot?:       boolean;            // ui — frequently used / hot path
  warn?:      boolean;            // ui — touched by a failing trace / flagged

  // Trace × code join
  touchedBy?: TraceTouch[];

  // Identity across renames (see §4.3)
  previousIds?: SymbolId[];          // chain of ids this symbol was previously known by

  // Layout hints (ui; a real renderer should run a force layout client-side)
  x?: number;                     // ui
  y?: number;                     // ui
}

interface TraceTouch {
  traceId: TraceId;
  nodeId:  NodeId;
  role:    "main-fix" | "proposed-refactor" | "read" | "edit" | string;
}

type SymbolId   = string;   // "setSid", "middleware", "auth.ts"
type SymbolKind = "module" | "fn" | "const" | "class" | "type";
Invariants
  • If kind === "module", parent is unset (or references a higher-level package/dir).
  • If kind !== "module", parent references a module (or a class, in future).

4.2 CodeEdge #

interface CodeEdge {
  from: SymbolId;
  to:   SymbolId;
  kind: EdgeKind;    // "calls" | "uses" | "reads" | …
  tag?: EdgeTag;     // overlay: "bug" | "proposed" | null
}

type EdgeKind = "calls" | "uses" | "reads" | "extends" | "imports" | "redirect-loop" | string;
type EdgeTag  = "bug" | "proposed";

The prototype encodes edges as tuples [from, to, kind, tag?]; storage uses the object form for extensibility. tag: "bug" renders red; tag: "proposed" renders dashed amber and ties back to an experiment branch via touchedBy.

4.3 Symbol identity across renames #

When a symbol is renamed (or moved between files), we allocate a new SymbolId and record a lineage link. The old id is retained so historical traces still resolve.

// Append-only log — one row per rename event
interface SymbolRename {
  from:    SymbolId;                   // old id (still resolvable via lookups)
  to:      SymbolId;                   // new id
  at:      ISOTimestamp;
  commit?: string;                     // git sha where the rename landed
  reason?: "rename" | "move" | "split" | "merge" | string;
}

Resolution rules.

  • Live lookups (tree view, code graph, joins from Node.files) always target the current id.
  • Historical references (a TraceTouch written when the symbol still had its old id) resolve via the chain: follow SymbolRename.from → to transitively until you land on a current id.
  • CodeSymbol.previousIds caches the chain for O(1) reads; rebuild when renames are appended.
  • On split / merge, the 1-to-1 chain is broken — renderers should surface the lineage diagram rather than silently pick a successor.

Why this shape. A single id would force rewriting history on every rename (expensive, destroys audit trail); a pure rename log without previousIds makes every read a graph walk. The combo gives fast reads, accurate history, and a single source of truth for lineage.

4.4 Derived — callers / callees derived #

interface CodeSymbolDerived {
  callers: SymbolId[];   // { e.from | e ∈ edges, e.to === this.id, e.kind === "calls" }
  callees: SymbolId[];   // { e.to   | e ∈ edges, e.from === this.id, e.kind === "calls" }
}

§5 Cross-entity relationships #

Trace 1 ─── * Node Node * ─── 1 Node (parent) Node * ─── * FilePath → CodeSymbol.file Node * ─── * SymbolId → CodeSymbol.touchedBy WikiPage.body ─── embeds refs like "trc_9f2a" → Trace.id (string match; no hard FK) SavedExperiment.specs[*].sourceNodeId → Node.id
  • Wiki ↔ Trace is intentionally loose: wiki pages reference trace ids as plain text. Upgrade to a typed link when we add auto-generated incident pages.
  • CodeSymbol ↔ Node is the most valuable join ("which traces touched setSid?"). Keep denormalized on the symbol side for fast reads; rebuild from Node.files + symbol-in-file index on writes.

§7 What's NOT in this model (and why) #

  • User accounts / auth / org — prototype is single-user; add when multi-tenancy lands.
  • Real-time streaming deltas — the prototype renders finished nodes. For live runs, add an append-only NodeEvent log (token deltas, tool-call progress); derive final Node state by folding events.
  • Annotations / human review — no comments / approvals yet. Design separately when the review workflow lands.
  • Cost budgets / alerts — sidebar shows 24h aggregates derived from Trace.totalCost; no budget entity.
  • Diffs — the Diff tab renders on-the-fly from input/output. If we need persistent patches, add a Patch entity linked from Node.

  parent: "n3",
  kind: "llm",
  label: "analyze callback",

  model: "claude-sonnet-4.5",
  provider: "anthropic",
  tools: ["read_file"],
  files: ["src/pages/auth/callback.ts"],

  outputTokens: 641,
  cost: 0.021,
  latency: 3180,
  ttft: 720,
  status: "ok",
  timestamp: "2026-04-20T14:22:17Z",
  highlighted: true,
  input: "<tool_result>…</tool_result>\n<user>Diagnose the loop.</user>",
  output: "Found the bug. In src/pages/auth/callback.ts line 47, …",
  toolCalls: [{ name: "read_file", args: { path: "src/pages/auth/callback.ts" }, result: "98 lines" }],
